Rules that follow

   1. Draft generation receives only corroborated and user_verified facts, plus
        source_supported claims in attributed form. It never receives inferred items as
       facts.
   2. Scores count source_supported evidence at lower weight than corroborated , and
       the explanation says which was used.
   3. Evidence older than a set age (to be chosen during VM1) is shown as stale and is
      excluded from drafts until refreshed.
   4. The excerpt check is stored with a content hash and fetch time, so a reviewer can see
       exactly what was fetched.
   5. VM1 measures two separate rates: how often source_supported claims are actually
       supported by their excerpt, and how often corroborated claims are actually true
       (section 5, test B).


3. Email sending under a send-only scope
The design chooses at-most-once sending: an ambiguous result becomes unknown , is
never retried automatically, and waits for a person to resolve it. A missed send is
acceptable; a duplicate is not. Bounce reading, reply sync and automatic sender-health
from bounce rates are removed from the MVP, because they need mailbox access we have
decided not to request.

What the sources show. Google's users.messages.send reference describes a method
that takes a message and returns a message; in the excerpts I could read there is no
idempotency key, so the design assumes Gmail provides none. I did not read the full
reference page, so Phase 0 includes confirming that. Other mail APIs advertise their own
idempotency headers (for example Resend), which is a reason not to assume Gmail has
one.

Preventing duplicates without native idempotency
   1. One logical send, one database row. A unique constraint on (workspace, recipient
       address, campaign) allows only one outreach message per recipient per campaign; a
       second approval attempt fails at the database.
   2. Claim before calling. The sender job moves the row from queued to sending with an
       atomic compare-and-set that records an attempt id. Only the job that wins the claim
       may call Gmail.
   3. No automatic retry at the send step. The job platform's retry setting is zero for this
       step. Earlier steps (rendering, suppression and eligibility checks) can retry freely.
   4. Crash recovery marks unknown . A row stuck in sending past a timeout is moved to
      unknown by a sweeper, never back to queued .
   5. Address hold. While any message to an address is unknown , no other message to that
       address can be claimed.
   6. Double-click and replay tests are acceptance criteria (section 5, test E).

The cost is that a real timeout needs a person. Because we cannot read the Sent folder
under gmail.send , there is no safe automatic check. That trade is deliberate.

Design consequences
       Each provider adapter has a may_persist_results flag, default false. With it false,
       the adapter returns results to the job in memory; the database stores only our query
       log (query text, provider, time, cost) and the candidate domains that we then fetch
       and check ourselves. Whether even a domain may be kept is part of the written
       confirmation to request.
       Evidence records are built from pages we fetch directly, so their storage is governed
       by our own handling of company websites, not by a search vendor's terms.
       "Do not contact" and "already rejected" memory relies on our own records of domains
       and addresses the user acted on, which is the user's own data.
       Contact discovery in VM1 uses team and contact pages on company websites only. A
       paid contact provider is added only after its rights are confirmed.


Alternative comparison in VM1
Exa and Brave run on the same ICPs. Compared on: relevant companies found per query,
cost per relevant company, share of results from which we can fetch own-site pages, and
the written storage and display position of each vendor. The comparison result decides
the primary provider; if neither grants storage in writing, the transient-only design stays.
